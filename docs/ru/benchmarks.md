# Бенчмарки

[Оглавление](../README.md) · [Потоковая обработка](streaming.md) · [Сжатие](compression.md) · 🇬🇧 [English version](../en/benchmarks.md)

Здесь хранится **измеренная базовая линия** однопоточной потоковой реализации. После каждого изменения производительности (многопоточность, более быстрое кодирование строф, новые кодеки, шифрование...) прогоните те же сценарии и добавьте новую колонку/раздел, чтобы результаты можно было сравнить.

## Как воспроизвести

```text
cmake --preset x64-release
cmake --build out/build/x64-release
powershell -ExecutionPolicy Bypass -File scripts\benchmark.ps1 -SizeMiB 100 -Data Random -Compression none
```

[scripts/benchmark.ps1](../../scripts/benchmark.ps1) генерирует входной файл, выполняет `encode`, `verify` и `decode`, проверяет, что восстановленный файл идентичен, и печатает строки Markdown (секунды, пропускная способность по входу, пиковая память). Параметры: `-Exe`, `-SizeMiB`, `-Data Random|Text`, `-Compression none|zstd|auto`.

Чтобы **сравнить несколько сборок** (до/после оптимизации), используйте [scripts/compare.ps1](../../scripts/compare.ps1): храните Release-бинарник каждого варианта и передайте их упорядоченным словарём, например
`$b = [ordered]@{ A = "a\bardzip.exe"; B = "b\bardzip.exe" }; .\scripts\compare.ps1 -Builds $b -SizeMiB 32 -Runs 5`.
Скрипт использует один общий вход и одну заранее созданную поэму, прогревочный запуск, чередование порядка и выдаёт медиану и диапазон. Не называйте это измерением холодного SSD: файловый кэш прогрет.

Правила честного сравнения: та же машина, «тихая» система, тот же тип сборки (Release), тот же сценарий. Числа Debug сравнивайте только с Debug.

Бенчмарки передают `--max-input 0`, потому что лимит входа по умолчанию — 16 МиБ ([обзор](overview.md)).

## Базовая линия 2 — Debug, 100 МиБ случайных, `none`

Измерено один раз, сразу после реализации потоковой обработки (первый стресс‑тест).

| Команда | Секунды | МиБ/с | Пик памяти МиБ |
|---|---:|---:|---:|
| encode | 362,5 | 0,28 | 12,0 |
| verify | 292,2 | 0,34 | 7,9 |
| decode | 221,9 | 0,45 | 7,9 |

Размер поэмы: 5 629 547 537 байт. Release примерно в **15–17 раз быстрее** Debug.

## Что говорят цифры

- **Память постоянна**: 5–12 МиБ независимо от размера входа (прежняя версия «всё в памяти» потребовала бы много ГБ на тот же файл).
- **Поэма ≈ в 53,7 раза больше хранимых данных** (случайные данные без сжатия): ≈ 54 байта UTF‑8 на байт данных. Именно это отношение использует оценка в сообщении `--max-input`.
- **Несжимаемые данные упираются в генерацию текста и запись на диск**, а не в CRC32 или zstd: ~4–5 МиБ/с входа — это ~250 МиБ/с текста поэмы.
- **Сжимаемые данные обрабатываются быстро**, потому что поэма крошечная (здесь 12 МиБ на 32 МиБ входа); основное время — zstd и CRC32.
- `verify` / `decode` не быстрее `encode`, хотя делают меньше «творчества»: они разбирают каждую строфу из текста (три строки, поиск по словарям линейным перебором) и пишут временный файл payload.

## Журнал оптимизаций

Каждый раз один и тот же сценарий: Release, 100 МиБ случайных данных, `--compression none` (поэма 5 369 МиБ). Пропускная способность — МиБ входа в секунду.

| Шаг | Коммит | encode с (МиБ/с) | verify с (МиБ/с) | decode с (МиБ/с) | Пик памяти МиБ |
|---|---|---|---|---|---:|
| Базовая линия 1 | `fbf540a` + потоковая обработка | 20,8 (4,80) | 28,2 (3,55) | 25,7 (3,89) | 5,4 |
| 1. Таблицы строк для всех 256 значений байта (`PoemEncoder` добавляет готовые строки) | – | 14,3 (7,01) | 17,8 (5,63) | 18,5 (5,40) | 5,9 |

Шаг 1 даёт для encode **−31 %** времени. verify/decode тоже ускорились (−37 % / −28 %), хотя декодер не менялся, — значит, значительная часть этого разброс между запусками (кэш диска, фоновая нагрузка): для этого шага сравнивайте только encode и повторяйте замеры, прежде чем делать выводы. Контролируемое A/B-сравнение ниже заменяет эту грубую оценку.

### Контролируемое сравнение шагов 1 и 2

Метод ([scripts/compare.ps1](../../scripts/compare.ps1)): три Release-бинарника из одних исходников, один общий вход и **одна заранее созданная поэма** для всех сборок, 1 прогревочный + 5 измеряемых запусков на сборку с чередованием порядка, указаны медиана и диапазон. Результаты относятся к **прогретому файловому кэшу** (это не холодное чтение с SSD). Перед замером скрипт проверяет, что результат encode каждой сборки побайтово совпадает с общей поэмой, а decode каждой сборки восстанавливает вход.

| Сборка | Изменение |
|---|---|
| A | до таблиц кодирования (`std::string` на каждую строфу) |
| B | таблицы кодирования (шаг 1) |
| C | таблицы кодирования + таблицы декодирования (шаг 2: `unordered_map<std::string, uint8_t>` для всех 256 первых и всех 256 вторых строк) |

32 МиБ случайных данных, `--compression none` (поэма 1 718 МиБ):

| Команда | Сборка | Медиана с | Мин–макс с | МиБ/с | Пик памяти МиБ |
|---|---|---:|---|---:|---:|
| encode | A | 6,21 | 6,11–6,65 | 5,15 | 6,0 |
| encode | B | 2,50 | 2,42–5,31 | 12,78 | 5,0 |
| encode | C | 2,52 | 2,44–3,25 | 12,72 | 6,0 |
| verify | A | 6,40 | 6,18–6,49 | 5,00 | 6,0 |
| verify | B | 6,54 | 6,33–6,62 | 4,89 | 5,0 |
| verify | C | **5,84** | 5,73–5,97 | 5,48 | 5,0 |
| decode | A | 6,44 | 6,27–6,56 | 4,97 | 5,0 |
| decode | B | 6,53 | 6,51–6,70 | 4,90 | 5,0 |
| decode | C | **5,82** | 5,72–5,88 | 5,50 | 5,0 |

То же сравнение A и B для encode на 100 МиБ (поэма 5 369 МиБ, 2 запуска): A 18,72 с (5,34 МиБ/с), B 12,79 с (7,82 МиБ/с).

Выводы:

- **Шаг 1 (таблицы кодирования)**: encode **в 2,5 раза быстрее** (−60 %) на 32 МиБ. На 100 МиБ выигрыш только −32 %, потому что выход 5,4 ГБ упирается в запись на диск: B там уже не ограничен процессором. Сборка A упиралась в CPU (~290 МиБ/с текста поэмы), B доходит до ~420 МиБ/с записи на диск.
- **Шаг 2 (таблицы декодирования)**: verify и decode **быстрее примерно на 11 %** (6,54 → 5,84 с и 6,53 → 5,82 с); диапазоны B и C не пересекаются, значит выигрыш устойчивый, но скромный. Поиск по словарю не был главной статьёй расходов: основное время уходит в другом месте (см. идеи ниже). Решение: таблицы **оставляем**.
- encode C = encode B (декодер там не участвует), пик памяти одинаков (5–6 МиБ) у всех сборок.
- Более ранние грубые числа в таблице выше (сделаны [scripts/benchmark.ps1](../../scripts/benchmark.ps1), 100 МиБ, один запуск) нельзя напрямую сравнивать с этими медианами.

### Шаг 3 — переиспользование строк строфы в декодере

Изменение (сборка D): `StanzaReader` хранит одну `Stanza` как поле и читает в неё три строки, так что ёмкость строк переиспользуется вместо трёх новых выделений на каждую строфу. Хеш-таблицы, CRC32 и размеры блоков не менялись. Сборки C и D, тот же метод, 32 МиБ случайных данных, 5 запусков после прогрева:

| Команда | Сборка | Медиана с | Мин–макс с | МиБ/с | Пик памяти МиБ |
|---|---|---:|---|---:|---:|
| verify | C | 5,73 | 5,49–9,19 | 5,58 | 5,0 |
| verify | D | **4,06** | 3,64–4,13 | 7,88 | 5,0 |
| decode | C | 5,82 | 5,58–5,90 | 5,50 | 5,0 |
| decode | D | **3,85** | 3,74–4,30 | 8,32 | 5,0 |

verify **−29 %**, decode **−34 %**; диапазоны не пересекаются, память не изменилась. Решение: **оставляем**. Это подтверждает догадку, что главной статьёй расходов декодера были выделения строк, а не поиск по словарю. Декодирование теперь около 8 МиБ/с — всё ещё медленнее encode (~12,8 МиБ/с на 32 МиБ).

## Идеи для проверки на этой базовой линии

| Идея | Ожидаемый эффект |
|---|---|
| ~~Убрать `std::string` на каждую строфу в `PoemEncoder`~~ **сделано (шаг 1)** | encode ↑ |
| ~~Заменить линейный поиск по словарю хеш‑таблицей~~ **сделано (шаг 2, +11 %)**; дальше: ключи `string_view` / идеальный хеш | decode / verify ↑ |
| ~~`LineReader` / `decode_poem_stream` создают `std::string` на каждую строку~~ **частично сделано (шаг 3, −29 % / −34 %)**: строки переиспользуются; чтение строк как `string_view` могло бы убрать оставшиеся копии | decode / verify ↑ |
| Табличный (slice‑by‑8) CRC32 вместо побитового | все команды ↑ (CRC считается 2–3 раза на байт) |
| Конвейер в потоках: чтение + CRC / сжатие / форматирование поэмы / запись | encode ↑ до скорости самого медленного этапа |
| Параллельный zstd (`ZSTD_c_nbWorkers`) | encode сжимаемых данных ↑ |
| Не использовать временный файл payload при decode для небольших payload | decode: меньше дискового ввода‑вывода |
| Новые кодеки / шифрование | измерить стоимость на МиБ относительно этих строк |

Добавляя строки, сохраняйте старые и указывайте хеш коммита и что изменилось, например `| Release | случайные | none | 100 | encode | 9,1 | 10,99 | ... | табличный CRC32 (abc1234) |`.
